# Pipelines — definition, launch, advancement, legs

The pipeline is the runnable business unit (ADR-0084 D4/D9, ADR-0105). This document covers
the machinery in `src/cairn/core/dispatch/` and `src/cairn/core/engine/pipeline*.py`. Exact trace:
[../golden-paths/pipeline.md](../golden-paths/pipeline.md).

## Purpose
Compose a pack's own flows, templates and operators into a DAG whose every step is a
governed `Run`, sequenced by the control plane — never by a graph runtime.

## Leg kinds (OBSERVED at `pipeline_bridge.py:859 _submit_step`)
| Kind | Ref shape | Executes via | Governance touchpoint |
|---|---|---|---|
| `gate` | `gate: <name>` (+ `predicate` or `show`) | no run; verdict recorded (`data` or `approved`); HITL → `awaiting_approval` + review | approvers from gate or pipeline `governance.approvers` (`required_approvers`), **enforced** at the approve door for a declared gate: a username or a role, owner/admin always, an unknown name → owner/admin only (#2393, `08-governance.md`) |
| `flow:` | `flow:<pack>/<name>` (data/ml `FlowDef`) | `_submit_flow_leg` → own `Run` → `execute_leg` → `DataflowEngine` | `enforce_flow_gate` on aggregate stage risk; budget reserve; policy-injected gates |
| `task:` | `task:<operator>` | `_submit_task_leg` → own `Run` → `_invoke_task_op` → executors include `in_process`, else refused (#2182) → `enforce_gate` → `op.run` | approval gate; **no budget reservation** (observed) |
| `template:` (agentic) | `<pack>/<template>` | `dispatcher.run_template` (LangGraph) | full dispatcher admission |
| `loop:` | nested steps | unrolled at runtime; `max_iterations` mandatory; `on_exhausted: gate` | each iteration = fresh runs |

## Does not own
Operator implementations, engine implementations, the console rendering (`console/src/views/Pipeline*.tsx`), the HTTP shape (`triggers/routers/{start,pipelines,runs,run_control}.py`).

## Public interface
Authoring grammar (`pipelines/*.yaml`); `POST /start`, `POST /pipelines/launch`, `GET /pipelines*`, `POST /pipelines/{id}/steps/{step}/{advance|approve}`, cancel; CLI `cairn pipeline {ls,show,explain,run}`, `cairn run`; Python: `launch_pipeline`, `resolve_start_ref` (`launch_workflow` was removed by ADR-0106 D1).

## Dependencies
`dispatch` → `core/<top>` (37), `engine` (32), `storage` (20), `operator` (14), `dataflow` (14), `bus` (10), `runtime` (7), `pack` (5), `triggers` (5 lazy), `obs` (4), `eval` (3), `approval` (3), `policy` (1), `playground` (1).

## Dependents
`triggers/routers/*` (23), `cli` (5), `runtime/temporal` (8), `engine` (8, reverse), operator `monitor_threshold` (drives launches).

## Side effects
Everything downstream: engines, operators, LLM calls, HITL notifications (`gate_notify.py`), bus publications, Temporal workflow starts.

## State
`PipelineRecord` (+ `step_state` cursor), one `Run` per leg, budget reservations, review store rows, target-concurrency slots (in-process events + Postgres locks), scheduler jobs.

## Entry points
`routers/start.py:111 start_anything`; `routers/pipelines.py:192 launch_installed_pipeline`; `cli/commands/pipeline.py:211 run_pipeline`; `dispatch/scheduler.py:55 fire_scheduled_workflow`; `operator_monitor_threshold/.../dispatch.py`; Temporal `PipelineWorkflow` re-entry on restart; `PipelineBridge._adopt_in_flight` (`:349`) on boot.

| In-process restart and cancel: an interrupted leg is not silently repeated (#1289, #2540, #2555) | OBSERVED, scoped: (1) on adopt (which lists only `running`/`paused` pipelines, `dispatch/pipeline_bridge.py:358`), a step persisted `pending`/`queued` with no run id takes an ACTIVE (`queued`/`running`/`awaiting_approval`) run that carries its `bundle_pipeline_id`/`step_id` (`_claim_unrecorded_leg_runs`, `:627`); the scan is active statuses only, through `RunStore.list`, capped at `SCAN_COUNT_LIMIT` = 500 per status (`_active_child_runs`, `:599`; `storage/protocols.py:388`). (2) A recorded or claimed `running` task, flow or template step first has its run read (#2555, `:414-418`). A run that is already terminal is settled through the normal terminal path after the step loop (`:444`; `_apply_terminal`/`_handle_terminal`, `:890`/`:912`): a `done` run's persisted output is the step's and the pipeline advances with nothing re-run; a `failed`/`cancelled` run fails the step and the pipeline as a live failure does. This includes a flow leg WITH a handle, which `_readopt_flow_leg` could not watch once its run was no longer `running`. Otherwise a `running` task leg goes through #1289 unchanged (`_resume_task_leg`, `:1789`): its run is settled `failed`, a `read_only` op is re-fired, any other op is parked `awaiting_advance`. A flow leg with a handle is re-adopted (`_readopt_flow_leg`, `:424`). A flow leg without a handle has nothing to re-attach to, and the H1 reconciler judges only heartbeat-stamped runs (`runtime/reconciler.py:119`); an in-process template run died with its process and `InProcessRuntime` has no boot recovery. Such a leg whose run still reads `running` (or is gone) has its run settled `failed` with the #1289 wording and its step parked `awaiting_advance` with `leg_parked_after_restart` (`_unadoptable`, `:534`; `_park_unadoptable_leg`, `:567`); a flow leg's park reason tells the person to check the engine for an orphaned job before advancing. A builtin-engine job cannot be orphaned this way any more: its runner kills its own process group when the server that owns it dies (#2614). EXCEPTION, remote jobs: a template run paused on a remote job is kept `running` by the dispatcher (`dispatch/dispatcher.py:1183`, `:1361` on re-pause) and is resumed through `RunDispatcher.resume_run` by the remote-job control loop (`operator/job_control.py:361`, started when `CAIRN_REMOTE_JOB_DURABLE` is set, `triggers/server.py:783`), so a template run with an ACTIVE remote job (`active_remote_jobs_for_run`, `operator/job_control.py:350`, the lookup run cancel uses, queried by active status), or whose jobs cannot be read, keeps the re-map. Under DBOS/Temporal a template run is also left re-mapped: DBOS recovers it at boot (`triggers/server.py:696`) and the reconciler reports its terminal. (3) The adopt-time `_advance` pass runs with `after_restart=True` (`:480`): EVERY step that pass would submit — including one made ready inside the pass by a `when` routing off or a gate leg passing (the flag rides the gate leg's recursion), and one made ready by a terminal applied in (2) — is submitted only when it is a gate leg or a `read_only` task leg (`_rerun_is_safe`, `:482`, same risk lookup `_task_op_risk`, `:1777`); every other leg is parked `awaiting_advance` with a `leg_parked_after_restart` audit event (`_park_after_restart`, `:494`, decided at `:1197`). So a step whose run already finished, or lies beyond the scan cap, fails CLOSED. Steps that do not become ready stay `pending`. Every restart park — this one, #1289's `task_leg_awaiting_decision` and (2)'s — sends the existing `awaiting_advance` gate notification with the park's reason, once per pause (`_notify_parked` → `_notify_gate`, `:517`/`:2861`). (4) A run terminal, live or from adopt, settles its step only while the step still names that run and is `running`/`queued`/`awaiting_approval` — the last because a paused run the step names (e.g. a template run claimed by (1)) can be resumed by the run-level door and finish, and its `done` is the step's (a paused record is advanced again, `_apply_leg_terminal`) — or `skipped`/`cancelled`, written before the run's `cancelled` is emitted by `_settle_cancelled_while_queued` (`:1950`) and `_settle_human_waits_on_cancel` (`:2483`) (`_terminal_applies`, `:967`). Any other terminal — a step re-run, parked for a person, or a refused store update announced anyway — is ignored with a `late_terminal_ignored` audit (`:946`). `leg.finished` fires only for a terminal that applies (or one arriving after its pipeline ended), never for a missing pipeline record, after the pipeline lock is released (`:962`). (5) `cancel_pipeline` (`:2369`) settles `cancelled` only the child runs at `awaiting_approval`, finalizer runs excluded, and emits `run.cancelled` only when the update landed (`_cancel_stranded_child_runs`, `:2430`). `queued`/`running` child runs are left to their own paths (`_settle_cancelled_while_queued`, `:1950`, for a queued leg); cancel is one-shot and never sees DEAD (ADR-0125 D4). A Temporal-owned pipeline gets the same settlement after its workflow is cancelled (`:2399`, #2555): nothing in `runtime/temporal/pipeline_workflow.py` or `pipeline_activities.py` handles a cancel — cancelling the workflow cancels the `pipeline_await_run` activity (`pipeline_activities.py:382`) and leaves the run as it was. A leg still `running` when its process dies after the cancel is settled by the reconciler once its owner is DEAD (next row); a leg with no owner (written before ADR-0125) is left to the one-off cleanup script (`scripts/ops/settle_dangling_runs.py`, ADR-0125 D6). Adopt (1)–(3) does not apply to Temporal-owned pipelines. Adopt is not leader-gated (#2555 item 6); since ADR-0125 a replica booting beside a live one only re-maps that replica's legs (next row) — (2) applies to LEGACY legs and, through the reconciler, to DEAD ones |

## [0.3.1] - 2026-10-26

A patch release: GPU time on a priced `compute.ssh` box is counted in the budget, and a public pipeline can start and stop its box. Everything is additive or internal; nothing that worked on 0.3.0 changes unless a pipeline runs on a `compute.ssh` connection that sets `hourly_usd`.

### Upgrade notes
- **Priced boxes are now checked at launch.** A pipeline with a flow leg on a `compute.ssh` connection that sets `hourly_usd` must give that leg a `timeout`, and the leg's worst-case cost must fit what its budget has left; otherwise the launch is refused before any record exists, with the reason. A connection without `hourly_usd` is "not priced" and launches as before. (ADR-0151, ADR-0152)
- **`cancelled` is a job state.** `remote/exec` and the builtin SSH engine report a cancelled job as `cancelled` (terminal, never retried) instead of a retriable death. A third-party consumer of `JobStatus` that treats any state other than `succeeded`/`failed` as running should treat `cancelled` as terminal. (ADR-0151 D9)
- **Another pack that registers `compute/acquire` or `compute/release`** must drop them in the same upgrade, or whichever loads last wins with a warning (see Added).
- The example pack `cairn-pack-hello` is 0.2.4 in this release (unchanged apart from the version).

### Added
- `compute/acquire` and `compute/release` ship in the builtin remote pack (`cairn-operator-remote`), so a public pipeline can start the EC2 instance a `compute.ssh` connection names after a person approved the spend, and stop it when the run ends (ADR-0151 D6, #201). They keep the refs, input and output schemas, risk classes (`acquire` `paid_compute`, rated high and passing the approval chokepoint; `release` `external_write`, never approval-gated), capabilities and reports of the platform's `cairn-operator-compute` 0.1.0, with no contract URI yet (D7). `release` is idempotent: an instance already stopped is a success, so a `finalizer: true` release can run again after a restart. `acquire` writes the `cairn:managed` lease tag (and `cairn:release-after` when `max_hours > 0`, and `cairn:acquired-by`) before it starts the instance, the reverse of the platform's order, so a crash between the two calls never leaves a running box that `cairn compute sweep` cannot see (D8). The operator contract `cairn.core.operator` re-exports the `compute_lifecycle` functions they call (`load_box`, `ec2_client`, `describe_state`, `stamp_lease`, `start_instance`, `stop_instance`, `wait_port_open`, `iso`, `BILLING_STATES`, `STOPPED_STATES`). **Upgrade note:** the platform's `cairn-operator-compute` must drop its copies of these two operators in the same release. If both are installed, the engine does not refuse to start: production loads operators non-strictly, so the second registration of each name replaces the first with a warning (`operator 'compute/acquire' re-registered`), whichever entry point loads last wins, and the lease-before-start order is not guaranteed. (ADR-0151 D6 says both installed would fail with `DuplicateOperatorError`; that holds only for a strict load, which no production path uses.)

### Changed
- On a pipeline cancel, a running flow leg on a box the pipeline releases (its recorded compute target is the `connection` of a `finalizer:` step providing `compute.release`) has its engine job cancelled before the finalizers run, so stopping the box is never the only kill (ADR-0151 D9). The leg's run still settles through its own path; a job cancel that fails is logged and audited (`pipeline.leg_job_cancel`, `sent: false`) and the release still stops the box. Other running legs are left alone, as before (#209). `remote/exec`'s cancel now writes a `cancelled` marker in the job's workdir before it kills the job, and its poll reads that marker first: a killed job reports `cancelled` (not retriable) instead of "remote process exited without an exit code" (retriable), so the leg is not relaunched and its run settles `cancelled`. The builtin SSH engine passes `cancelled` through. A job that dies without the marker is still a recoverable death. `cancelled` is now a documented `JobStatus` state (terminal, never retriable): the remote-job control loop closes such a record `cancelled` and resumes its run with `{"status": "cancelled"}` (it no longer counts it as running or hands it to the learning gate), `run_job_lifecycle` ends with the new `JobCancelled` (a `JobFailed`), a resumed durable node raises it instead of pausing again, and `dataflow/run` and `ml/run` pass an engine's `cancelled` through. A cancel that reaches a job before its process has started (no pid yet) marks it `cancelled`, kills nothing and logs it; the pull lane (`/jobs` heartbeat) does not carry `cancelled`. (#209)
- A flow leg whose compute target is a `compute.ssh` connection with `hourly_usd` is priced (ADR-0151 D1–D5, as read by ADR-0152). Only the builtin engine's target is priced: another engine's `<kind>_target`, such as a legacy Metaflow metadata root, reads "not priced" and launches as before. The launch door estimates it at `hourly_usd × timeout`, refuses the launch before any record when the priced legs' sum does not fit what the budget has left (the cap less the series' live holds; nothing is reserved at the door) or when a priced leg declares no `timeout` ("declare a timeout to price this leg"), and records each leg's estimate, rate, hours and connection under `admission.cost_estimate`. The leg reserves that recorded figure, even if the connection's rate changes later. The approval gate before the first priced leg shows `estimate_usd` and `estimate_basis` in its evidence. Every attempt settles `hourly_usd ×` its wall-clock on success, failure, timeout or cancel (instead of releasing a failed attempt), and the leg's `Run.cost.gpu_usd` is the sum of its attempts; engine-reported cost stays in `llm_usd`. The estimate is the bounded worst case: a priced leg inside a loop counts `max_iterations` times, and a leg that may retry counts each attempt (a declared `retry: {max_attempts}`, else 1 for `ml` and 2 for `data` legs); each attempt still reserves one attempt's figure. A `governance.budget.usd` with no `series` is checked at the door against the cap alone; such a pipeline's legs reserve nothing, so the door is its only budget check. A price that cannot be read (the target selection, the connection store, a target connection that is not registered, a malformed `hourly_usd`) refuses the launch with the reason; only a target with no `hourly_usd`, another connection kind or a `worker:` pool reads "not priced", never $0. An adopted leg after a restart settles the hold its dead process left, at its window less what the run already settled; the backoff between two fresh attempts is not billed, and an adopted window (from the leg's start) over-estimates box time rather than counting it twice (ADR-0152). A pipeline that launched before can be refused now when its priced legs exceed its budget, have no timeout, or cannot be priced. (#200, #211)

### Removed
- `PipelineBridge.run_bundle`, an internal method with no callers since the launch door replaced it; `start_pipeline` keeps the Temporal routing it duplicated. Comments and test reasons in the source cite internal issues as plain text. (#205, #210, #214)

## [0.3.0] - 2026-10-24

A minor release because it contains breaking changes: the artifact registry migrates its storage in place (ADR-0147, ADR-0148), and the Helm chart's pull-worker values change (`docs/compatibility.md`: a break before 1.0 is a MINOR bump with migration notes). See Upgrade notes.

Workspace-scoped artifact tags and reads, a hardened SSH path for remote training boxes, a Secret of its own for the Helm chart's pull worker, and launch-time refusals under the Temporal runtime. The artifact registry migrates on first start, and the Helm chart changes for pull-worker users: read the upgrade notes before upgrading.

### Upgrade notes
- **Upgrade every server process that shares one database together.** The artifact registry migrates in place on the first start of the new version (ADR-0147, ADR-0148; see Migration). An older process on a migrated database registers artifacts no workspace can see, drops (SQLite) or fails on (Postgres) their parents, cannot promote a tag, and still reads across workspaces.
- **Rotate credentials forwarded to `compute.ssh` boxes.** Deployments that ran flow legs on a `compute.ssh` box before this release should rotate `MLFLOW_TRACKING_PASSWORD` and any other value forwarded to those jobs. Job records written earlier hold those values; `GET /pipelines/{id}` now shows them as `[hidden]`, and stored records are not rewritten (ADR-0149).
- **The builtin SSH engine has no default image.** Image mode needs an image named (the `compute.ssh` connection's `image`, `remote_image` or `CAIRN_TRAIN_IMAGE`); otherwise the leg is refused before submit. `auto`, the default, runs the box's virtualenv when no image is named (ADR-0150).
- **Helm, breaking for pull-worker users** (`pullWorker.enabled=true`): the chart refuses to render without `pullWorker.token` or `pullWorker.existingSecret`; the worker has its own ConfigMap and ServiceAccount (`<release>-pull-worker`); a cloud identity binding (IRSA trust policy, GKE Workload Identity binding, EKS Pod Identity association) must be keyed to the new ServiceAccount name; `env.extra` keys the worker's jobs rely on move to `pullWorker.extraEnv` (credentials to the worker's Secret). See Breaking (Helm chart).
- **`CAIRN_RUNTIME=temporal`** refuses at launch a pipeline with a `task:` leg or a `finalizer:` step, before any record exists (HTTP 403, exit 3). Run such pipelines under `inprocess` or `dbos`.
- **New:** `remote_env` (control-plane variables forwarded to an SSH job by name), comma-separated values for `type: list` inputs, and `cairn ls <pack>` listing the pack's deployment profiles.

### Breaking (Helm chart)
- A chart with `pullWorker.enabled=true` and neither `pullWorker.token` nor `pullWorker.existingSecret` (a whitespace-only token counts as unset) now refuses to render. Upgrade: mint a worker-pool token (`cairn remote worker-token --name <pool>`) and set one of the two; anything else the worker's jobs read from the control plane's Secret must be put in the worker's own Secret. (#194)
- The pull worker no longer reads the shared ConfigMap or the release's ServiceAccount. It stops receiving the database DSN family, `OTEL_EXPORTER_OTLP_HEADERS`, `env.extra` (apart from the `CAIRN_ENGINE_URL` / `OBS_ENGINE_URL` fallback), `CAIRN_RUNTIME`, `CAIRN_REQUIRE_AUTH`, `CAIRN_TEMPORAL_ADDRESS` and `CAIRN_CHECKPOINTER`. Upgrade: `env.extra` keys a worker's jobs relied on move to `pullWorker.extraEnv` (or the worker's Secret, for credentials). The worker's ServiceAccount is now `<release>-pull-worker` (or `pullWorker.serviceAccount.name` with `create: false`), and cloud-side bindings are keyed to that name: an IRSA trust policy, a GKE Workload Identity binding or an EKS Pod Identity association must be updated for it, not only the annotation moved to `pullWorker.serviceAccount.annotations`. A ConfigMap, ServiceAccount or Secret already named `<release>-pull-worker` collides. (#194)

### Migration
- **Artifact registry (ADR-0147, ADR-0148).** The first start on an existing database migrates it in place, once: SQLite rebuilds `artifact_tags` onto the key `(workspace_id, name)` and Postgres swaps its primary key, with every existing tag in `default`; the new `artifact_owners` table is backfilled so that `default` owns every existing artifact, as do the workspace of the run that produced it (when that run is in the same database) and every workspace that registered a dataset version of it, each with the artifact's existing registration; `artifact_parents` is rebuilt per workspace, each existing parent going to every owner of its child. Single-workspace deployments see no change. Upgrade every process that uses the registry together. An older version on a migrated database registers artifacts no workspace can see, drops (SQLite) or fails on (Postgres) their parents, cannot promote a tag, and still reads across workspaces. A tag promoted from another workspace before the upgrade is now in `default`; promote it again in its workspace. A library or route that calls the registry outside any workspace scope passes `workspace_id=`. (#192)

### Added
- A pipeline input declared `type: list` takes a comma-separated string as well as JSON: `-i report_to=mlflow,wandb` gives `["mlflow", "wandb"]` (items trimmed, empty items dropped). The launch door types it, so the CLI, the console and schedules agree, and `cairn pipeline explain -i` shows the typed value and refuses what the launch refuses, declared defaults included. A value that parses as JSON keeps the JSON rule; a value that opens with `[` but is not valid JSON, and one with no items (`-i report_to=`), are refused as before. An empty list is `[]`. (#197) (#208)
- `cairn ls <pack>` lists the deployment profiles the pack ships (`profiles/*.toml` beside its `pack.toml`), each with its `visibility` and its absolute installed path, so `CAIRN_PROFILE` can be set without looking in site-packages. `--json` carries the same under `profiles` (`name`, `path`, `absolute_path`, `visibility`). (#196) (#208)
- `remote_env` (`[profile.backends]`, or `CAIRN_REMOTE_ENV`): names of control-plane environment variables the builtin SSH engine forwards to the job on the box, each when set (for example `CAIRN_CHECKPOINT_BUCKET`, `CAIRN_CHECKPOINT_PREFIX`, `AWS_DEFAULT_REGION`). A name containing `KEY`, `SECRET`, `TOKEN` or `PASSWORD`, a malformed entry, or one the engine sets itself refuses the leg before submit, naming the variable (a malformed entry only by its position) and not its value. Unset, nothing beyond the existing set is forwarded. (#193)
- An engine may declare `needs_durable_inputs = True` (the builtin SSH engine does): the leg executor then resolves the leg's `dataset:` refs to their durable copies (ADR-0149). An engine that does not declare it is treated as co-located. (#193)
- The registry catalog lists a pack that ships pipelines and no agentic (`flows/*.md`) flows as a `domain_pack` with its `pipelines`, installed when one of them is present as `<pack>/<pipeline>` (it was left out of the catalog). Finding them lists pipeline files and reads pack manifests; it parses no pipeline. Packs with agentic flows stay `template_pack`, unchanged. A live `domain_pack` carries no `install` name, so a catalog entry's distribution name is kept when the two merge. (#167)

### Changed
- Under `CAIRN_RUNTIME=temporal`, the launch door refuses a pipeline with a `task:` leg or a `finalizer:` step before any record exists, naming each such step and pointing to `inprocess` or `dbos`: HTTP 403 from `/pipelines/launch` and `/start`, exit 3 from `cairn pipeline run`, and a reported problem in `cairn pipeline explain`. The Temporal pipeline owner does not run either yet, so such a pipeline used to start and fail when it reached the step. The check reads what the owner declares it runs (`cairn.core.runtime.temporal.PIPELINE_OWNER_LEG_KINDS`, `PIPELINE_OWNER_RUNS_FINALIZERS`). `inprocess` and `dbos` are unchanged. (#199, ADR-0151 D10) (#208)
- The builtin engine's SSH dispatch has no built-in container image. Image mode runs only an image named by the `compute.ssh` connection's `image` or by `remote_image` / `CAIRN_TRAIN_IMAGE`. When the leg's mode resolves to image and no image is named, submit refuses the leg before anything reaches the box, with a message naming the settings to change; for a connection's own `mode = image` it names the connection's `image` and `mode`. A connection's `mode` and `image` still override the environment per box. `auto`, the default, runs the box's virtualenv when no image is named, as before. `cairn doctor` reports each compute target's execution unit from the connection and the environment's `remote_exec_mode` / `remote_image`, in the engine's order: venv is OK with no image suggestion, and image mode with no image anywhere fails the row. `operator_dataflow.engines_ssh.DEFAULT_TRAIN_IMAGE` is removed. (#204, ADR-0150)
- Sign-up, a Google or GitHub sign-in that would create an account, and invite redemption refuse a username or email equal to the deployment admin's name (`CAIRN_API_USER`, `admin` when unset), compared trimmed and case-insensitively. The name reads as taken (`already_registered` / `username_taken`); nothing is created and the invite stays usable. (#190)
- With auth on, a durable remote job started from an operation node (`CAIRN_REMOTE_JOB_DURABLE`, pushed or on a `worker:<pool>` target) is recorded under the workspace in scope; with no workspace in scope the node is refused before anything is registered or dispatched, instead of recording the process default. (#190)
- A flow leg resumes only from a checkpoint a run of its own workspace relayed. A checkpoint whose producing run cannot be read is not used, and the leg starts from the beginning. (#190)
- Artifact tags belong to a workspace (ADR-0147). A tag is keyed by workspace and name, so each workspace has its own `prod`; `resolve` reads and `promote` moves only the tag of the workspace named (`workspace_id=`) or in scope, and `promote` refuses an artifact that workspace did not register (`KeyError`, the same answer as an unknown id). (#192)
- An artifact is visible only to the workspaces that registered it (ADR-0148). Every registration is kept per workspace: identical bytes registered by two workspaces stay one content-addressed identity, and each workspace reads only its own registration (URI, durable copy, stats, schema, producing run and job, account, time) and the parents it declared. `get`, `find_by_uri`, `list_artifacts`, `resolve` and `lineage` answer only from the workspace's own registrations (another workspace's reads as not found), the lineage tree walks only into the workspace's own artifacts, and a dataset version can name only an artifact its workspace registered. A leg's outputs, URI parents and relayed checkpoints are registered and looked up in its run's workspace, so a dataset reference or a checkpoint resume points at the workspace's own copy. `cairn doctor` checks the registry of the process's workspace (`CAIRN_WORKSPACE`, else `default`). (#192)
- With auth on, an artifact registry call (`register`, `get`, `find_by_uri`, `list_artifacts`, `lineage`, `resolve`, `promote`) with no `workspace_id=` and no workspace in scope raises `WorkspaceScopeRequired` before anything is read or written. (#192)
- A `dataset:` ref read by a flow leg on a `compute.ssh` box resolves to the version's durable copy (`durable_uri`, the object store) when the workspace's own registration has one (ADR-0149). Any other leg still gets the registered location, unless that is a local path that no longer exists and a durable copy exists. The registration itself is unchanged. (#193)
- A flow leg on a `compute.ssh` box (the builtin engine with a `<kind>_target`) is refused before submit when a dataset version it reads exists only at a control-plane path (`file://…#sha256=…` or `/…#sha256=…`); the error says how to give the version a durable copy. A plain local path from an upstream leg is still uploaded. (#193)
- `remote/exec` creates the job's `runner.sh` exclusively with mode 0600, after removing a stale copy; if a copy is still there, the submit fails instead of reusing the file. (#193)
- The builtin SSH engine's job handles no longer record forwarded environment values: the persisted handle keeps the exec input without its environment and lists the forwarded names (`env_names`). Job records written before this release may still hold those values, including `MLFLOW_TRACKING_PASSWORD`. `GET /pipelines/{id}` no longer shows them: each env value in a step's job handle reads `[hidden]` and the names stay; stored records are not rewritten. The values were readable before this release, so deployments that ran flow legs on a `compute.ssh` box should rotate those credentials. (#193)
- The SSH engine's refusal of control-plane-only dataset versions also looks inside nested config values and the spec's own config, and treats every `file:` URI form as local. (#193)
- The example pack `cairn-pack-hello` is 0.2.3 in this release (0.2.1 shipped it as 0.2.2).

### Changed (Helm chart)
- The Helm chart's pull worker reads its worker-pool token (`CAIRN_ENGINE_TOKEN`) from a Secret of its own (`pullWorker.token`, rendered into `<release>-pull-worker`, or `pullWorker.existingSecret`) and no longer reads the control plane's Secret (`CAIRN_JWT_SECRET`, `CAIRN_API_PASSWORD_HASH`, `POSTGRES_PASSWORD`, the model key, the SSH key). Its settings come from a ConfigMap of its own (an allowlist: `CAIRN_ENGINE_URL`, `CAIRN_BACKEND`, `CAIRN_PROFILE`, `MLFLOW_TRACKING_URI`, `OTEL_EXPORTER_OTLP_ENDPOINT` and the `CAIRN_ARTIFACT_S3_*` endpoint, bucket and region, plus the new `pullWorker.extraEnv`), so it receives no database settings, no OTEL headers and no `env.extra`, and it runs under a ServiceAccount of its own with no API token mounted (`pullWorker.serviceAccount.annotations` for its cloud identity). The token is trimmed. A `pullWorker.extraEnv` name that looks like a secret or a database setting, or a value with a password in a URL, refuses to render (names and URL credentials only; other credentials belong in the worker's Secret). `pullWorker.serviceAccount.create` / `.name` let a deployment name a pre-provisioned ServiceAccount, never the control plane's. Rendering refuses a token equal to `secrets.obsJwtSecret`, `existingSecret` set to the control plane's Secret, both values at once, and a non-string token; `cairn deploy doctor --values` reports the same cases (it warns where the release name is unknown). Notes: `deploy/helm/cairn/README.md`. (#194)

### Fixed
- `cairn pipeline show` (including `--plan`) and `explain` resolve a bare ref shared with a flow to the declared pipeline, as `pipeline run` does. The `run` argument help now states that a bare flow without a pipeline is refused (ADR-0106 D1, #113). Data/ML flow YAML already validates through the flow parser; new CLI controls cover valid and unknown-stage files. (#186)
- A pipeline step whose required wire resolves to nothing fails the pipeline and stops there: no later step starts on the failed record, `advance_step` records no approval and rejects the step's review with the cited reason, and the failure is announced once (including after a passed gate step). (#190)
- With auth on, a re-adopted leg refused because its record names no workspace (a flow leg re-attached after a restart, the Temporal flow-leg activity, the remote-job control worker's poll and relaunch) cancels the engine job recorded for it, best-effort, instead of leaving it running unwatched. (#190)
- Cancelling a job on a `compute.ssh` box (`remote/exec`, the builtin SSH engine) and pulling its checkpoints back authenticate with the connection's `PRIVATE_KEY`, the credential submit used, instead of `SSH_PRIVATE_KEY` from the control plane's environment. The job handle records the connection's name and account (and the workspace), and cancel resolves the connection in that account, so it also works with no workspace in scope (a learning-gate abort, a run cancel). The connection the handle names is used even if the engine's target changed since. A job handle recorded before this release, which names no connection, uses the engine's target, else `SSH_PRIVATE_KEY`. When the box cannot be reached, cancel and pull-back log a warning naming the host, workdir and connection, and a cancel is reported as failed (`cancel_recorded_job` returns `False`; a run cancel does not count the job) instead of failing silently. ## [0.2.1] - 2026-10-23

A patch release: two additive core features for the training and dataset-preparation packs of cairn-extensions (cairndev-sh/cairn#187). Nothing that worked on 0.2.0 changes; a result or pipeline that uses neither feature reads and runs as before.

### Added
- A dataflow stage can return several products (ADR-0141): `outputs: [<name>, …]` with flat `outputs.<name>.output`, `.content_hash`, `.kind`, `.rows`, `.bytes`, `.register_as` and `.register_role` stats. Each name becomes an artifact descriptor in the new `DataflowResult.named_outputs`, with the stage's parents; `output_artifacts` still holds one descriptor per stage, and the next stage still descends from the stage's own product. A split stage can register its train, val and test files as three dataset versions from one stage. `named_outputs` is left out of the result's JSON while empty, so a run without named products is read the same by an older control plane. A stage that returns no `outputs` is unchanged.
- Dataset-version registration from a flow takes the role a stage gives (`register_role`), which may be `training`, `validation` or `test`; any other role, `golden` included, refuses the leg before anything registers. Without it the version keeps the dataset's default role, as before. The holdout door therefore sees a test split a flow registers as `test`.
- A pipeline input may declare the role of the dataset version it takes (ADR-0146): `role: training | validation | test | golden` and `verdict: required`. The launch door then refuses a value that is not a registered `dataset:` ref, a version with another role (a test set passed as training data), or one with no intake verdict when one is required, before any record exists, and records each check under `admission.expectations`. An unknown role or another `verdict:` value fails when the pipeline loads. A pipeline that declares neither is decided as before.

### Changed
- The example pack `cairn-pack-hello` is 0.2.2 in this release (0.2.0 shipped it as 0.2.1).

## [0.2.0] - 2026-10-23

A minor release: it changes behaviour that operators, operator packs and library callers rely on (`docs/compatibility.md`: a break pre-1.0 is a MINOR bump with migration notes). Single-node and auth-off deployments, where everything belongs to the `default` workspace and account, are unaffected by the workspace, tenant and dataset changes below.

### Breaking
- **No workspace in scope is refused with auth on.** Resolving a connection, a secret or a dataset reference with auth on and no workspace in scope raises `WorkspaceScopeRequired`; it no longer resolves as the deployment. A template run, resume, pipeline leg or remote-job poll whose record names no workspace, or a workspace no store holds, is refused; a pipeline step whose record names no workspace ends failed (verdict `workspace_unresolved`) and fails its pipeline once. `ctx.launch` with no workspace in scope is refused.
- **A tenant run resolves only its own account's connections and secrets.** A connection name that only the deployment holds no longer resolves for a tenant's run, the deployment's bound SecretStore is not read for a tenant run (ADR-0143), and a tenant connection resolves only secret references stored for its account: a bare environment-variable name, `${env:NAME}`, the deployment's stored secrets and a reference stored before account namespacing resolve to nothing.
- **A tenant run's declared secrets arrive in `ctx.secrets`, not the process environment.** An operator that reads a credential from `os.environ` in a tenant run receives none.
- **`mcp_server_spec`, `resolve_corpus_source` and `index_workspace_corpus` refuse by default.** A stdio MCP server needs `allow_stdio=True`; an http/sse URL that fails the address guard (loopback, link-local, cloud metadata, or a private address unless `CAIRN_PROBE_ALLOW_PRIVATE` is set) needs `allow_private_network=True`; a `file://` source, a local path, or an ssh or `file:` git remote needs `allow_local=True`. Without `allow_private_network` the spec carries a no-redirect client factory and is not JSON-serialisable. A tenant corpus clone ignores the server's system and global gitconfig.
- **Knowledge collection keys change for some workspaces and long pgvector names.** A workspace's collections carry the prefix `ws_<id>__`, with the id's dashes turned into underscores, when the id is a lowercase slug (`[a-z0-9]` runs joined by single dashes) of at most 40 characters; such workspaces, and `default` (whose names are bare), keep their collections. Any other id (not a slug, or a slug longer than 40 characters) now uses `ws__<hash>__`, the first 16 hex characters of the id's SHA-256, so its corpora and episodic memory start empty under the new names. A pgvector collection whose name is longer than 63 bytes is stored in a new hashed table (`pg_table_name`) and starts empty. New workspace ids are capped at 40 characters and corpus names at 48 (`add` raises `ValueError` for a longer one).
- **Dataset references resolve within the workspace.** `dataset:<name>`, a pinned `@N` and `@latest` see only the run's workspace's versions; another workspace's version reads as not found, and `@latest` is the workspace's own newest version. The `default` workspace no longer resolves or lists other workspaces' datasets.
- **`pipeline.launching` fails closed.** When a `cairn.run_hooks` provider is installed, the new event fires on every pipeline launch, and a provider that raises anything other than `AdmissionRefused` on it refuses the launch. A provider that raises on events it does not expect therefore refuses every pipeline launch. A provider entry point that fails to load still fails open on every event: it is skipped, recorded (`run_hook_load_failures`) and shown by `cairn doctor`. Every other event, `run.admitting` included, still fails open.
- **Claiming pull-lane work needs a worker credential.** With auth on, `POST /jobs/claim` and job heartbeats take a worker-pool token or the deployment admin's (`CAIRN_API_USER`) token; a signed-in user's token gets `403`. `POST /registry/install|uninstall` need the deployment admin. Deciding a paused saga through `POST /triggers/approve/{workflow_id}` needs an action handler that implements `workspace_of` for anyone but the deployment admin.

### Migration
1. **Pull workers (auth on).** Where `CAIRN_JWT_SECRET` is set, mint a token per pool with `cairn remote worker-token --name <name> [--days N]` (default 30 days) and restart each worker with `cairn worker --pull --token <that token>`.
2. **Tenant connections and secrets.** Create, in each tenant account, every connection its runs use that only the deployment holds. Enter again the credential of any tenant connection created before account namespacing (new references are `cairn://secrets#<account>/<conn>-<KEY>`). Change operators that read credentials from `os.environ` to read `ctx.secrets`.
3. **Code outside a request or a run (auth on).** Scripts and background jobs that resolve connections, secrets or datasets must enter a workspace first (`with workspace_scope("<workspace>"):` from `cairn.core.workspace`), or they get `WorkspaceScopeRequired`.
4. **Library callers of `mcp_server_spec`, `resolve_corpus_source`, `index_workspace_corpus`.** Pass `allow_stdio=True`, `allow_private_network=True` or `allow_local=True` only for specs and sources the deployment itself owns. If corpus clones need a proxy or a private CA, set `HTTPS_PROXY`, `SSL_CERT_FILE` or `GIT_SSL_CAINFO` in the environment instead of `http.proxy` / `http.sslCAInfo` in the gitconfig.
5. **Re-index affected knowledge.** For a workspace whose id is not a slug or is longer than 40 characters, run `index_workspace_corpus` for each of its corpora; the new prefix gives new catalog keys, so the incremental index embeds everything. For a pgvector collection whose name exceeds 63 bytes, a git-sourced workspace corpus re-embeds on its next index; a corpus read from a stable path (a `file://` workspace corpus, a pack corpus, a directory indexed from the CLI) is skipped while its catalog says it is indexed, so first `DELETE FROM rag_catalog WHERE corpus = '<key>'` (`<key>` is `<pack>/<corpus>` for a pack corpus, or `ws:<workspace>/<corpus>` for a workspace corpus, preceded by the workspace's collection prefix outside `default`), then run `index_corpus` / `index_all` (pack corpora) or `index_workspace_corpus` (workspace corpora). Index again any workspace corpus indexed from outside its workspace before this release (for example from the CLI). Old tables are left in place; drop them when no longer needed.
6. **Datasets (multi-workspace).** Register each dataset in every workspace that uses it; refs and `@latest` no longer reach another workspace's versions.
7. **Run-hook providers.** Return early on events a provider does not handle, and on `pipeline.launching` raise only `AdmissionRefused(reason)` to refuse.
8. **Console sign-ins.** Nothing to run: the `refresh_tokens` table is created on first use. Behind a TLS-terminating proxy, or one that rewrites `Host`, set `CAIRN_PUBLIC_URL` to the browser-facing `https://` origin, so the `cairn_refresh` cookie is `Secure` and refresh and sign-out pass the same-origin check. `CAIRN_REFRESH_TOKEN_DAYS` (default 30) sets how long a remembered sign-in lasts. A rotated refresh token sent again within 10 seconds of its rotation renews (ADR-0144); if the token that replay displaced is presented 10 seconds or more later, the sign-in ends for both holders and the server logs the warning "superseded refresh token presented" (ADR-0145).

### Added
- A run hook can inspect and refuse a pipeline launch before it starts. The `cairn.run_hooks` entry-point group has a new event, `pipeline.launching`, fired by the launch door that every pipeline launch goes through (`POST /start`, `POST /pipelines/launch`, `cairn pipeline run`, schedules, watches, webhooks, event triggers, `ctx.launch`, and a template run wrapped in its one-leg pipeline) after the policy gates, the service doors and the admission decision, and before the pipeline record exists. Its payload carries `pipeline_ref`, `workspace_id`, `account_id` (empty when it cannot be resolved), `environment`, `source`, `trigger`, `preset`, `inputs` (the values the launch will run with) and `supplied` (what the caller and the preset supplied); `trigger`, `inputs` and `supplied` are read-only copies. A provider refuses by raising `AdmissionRefused(reason)`; the caller gets the existing admission refusal (`AdmissionRefusedError`: `403` with the decision from both HTTP doors, exit code `3` from the CLI) and no record is created. Unlike every other run-hook event, `pipeline.launching` fails closed: a provider that raises anything else refuses the launch with a reason naming the provider. With no provider installed nothing is fired and launches are unchanged. Every other event keeps its behaviour, `run.admitting` included (a provider failure is logged and ignored). Upgrade: an installed provider that raises on an event it does not expect now refuses every pipeline launch; providers should return early on events they do not handle.
- Console sign-ins renew and can be ended on the server (ADR-0142). `POST /token`, the Google/GitHub sign-in landing and `POST /auth/signup` still return the same access token in the same place, and now also set a `cairn_refresh` cookie (`HttpOnly`, `SameSite=Strict`, `Path=/auth`, `Secure` when the public URL is https) holding an opaque token whose SHA-256 is all the server keeps. `POST /auth/refresh` (with the header `X-Cairn-Refresh: 1`, from the server's own origin) trades it for a new access token and a new cookie; a cookie that was already used revokes every token of that sign-in, unless it is sent again less than 10 seconds after it was used and the sign-in is still live: then it renews (a lost response, two tabs refreshing at once), the token issued for the first use stops working, and a replay inside those 10 seconds is not treated as theft at first (ADR-0144); if the token that replay displaced is sent 10 seconds or more later, the sign-in ends for both and the server logs a warning (ADR-0145). `POST /auth/logout`, with the same header from the same origin, ends the sign-in (204, idempotent, no access token needed). A sign-in's lifetime is fixed when it starts; refreshing does not extend it. `POST /token` takes an optional `remember` form field: true (the default) keeps the sign-in for `CAIRN_REFRESH_TOKEN_DAYS` (new setting, default 30), false makes the cookie a session cookie and the server honours it for 12 hours. Changing a user's password or disabling them ends all their sign-ins. Sign-ins are stored in a new `refresh_tokens` table (SQLite or Postgres, created on first use). With auth off nothing changes: no cookie, and both new routes answer `400` like `/token`. `cairn remote login` is unchanged. An access token already issued stays valid until it expires (30 minutes by default) after a sign-out.
- `cairn.core.dataflow.fidelity`: the deterministic, recorded subsample a flow stage takes (`Fidelity`, `plan`, `row_hash`, `digest_rows`). The kept rows depend only on the corpus, the seed and the row count, never on row or key order, and the digest records which rows were kept, so two runs on the same subsample are provably comparable. Operator packs that sample (training, dataset checks) import it from here instead of carrying their own copy.

### Security
- Dataset references resolve within the run's workspace. A `dataset:<name>[@<version>|@latest]` input of a pipeline leg (flow and task legs, in-process and under the Temporal owner) resolves only that workspace's versions: another workspace's name, pinned version or head is "not found", the same as an unknown ref, and `@latest` is the workspace's own newest version. With auth on, resolving outside any workspace scope is refused (`WorkspaceScopeRequired`). The registry's by-name reads (`get_dataset_version`, `list_dataset_versions`, `get_dataset_version_meta`, `list_datasets`) and writes (`set_dataset_version_meta`, `set_dataset_version_verdict`) take an optional keyword `workspace_id` and otherwise answer in the current workspace (the request's or the run's); a write never changes another workspace's version. The launch doors (holdout, intake, admission) and the dataset watch read the launching workspace's versions. Any workspace may register under any name; its versions are visible only to it and do not move another workspace's `@latest`. Re-registering identical bytes compares with, and updates only, the registering workspace's own head. A leg's export registers, and its intake verdict is stamped, in the run's workspace; with auth on and no workspace in scope the registration is refused. Shared per name across workspaces: version numbers (one sequence per name, so a workspace's versions of a name need not be consecutive), and the name-level metadata row (`set_dataset_meta`: description, labels, default role, schema and column mapping), whose description and labels `list_datasets` returns; a version registered without an explicit role, schema or column mapping inherits the name's defaults whichever workspace registers it. Registrations of one name are serialised: on Postgres by a per-name transaction advisory lock, so concurrent registrations get consecutive numbers instead of a duplicate-key error; on SQLite a number another process took first is re-read and retried a bounded number of times. No schema change; versions written before this release keep their recorded workspace (`default` for rows without one). Single-node and auth-off deployments, where everything belongs to `default`, are unchanged. Behaviour change for multi-workspace deployments: the `default` workspace no longer resolves or lists other workspaces' datasets.
- Every route that writes a workspace's records or starts work checks, at the route, that the caller may write in the workspace it acts in, and answers `403` ("not a member of workspace …") when the caller's account does not own it. `POST /start`, the workspace variable writes and `POST /triggers/inbox/replay` already checked this; the route-level check now also runs, alongside the workspace middleware, on `POST /pipelines/launch`, saving and deleting launch presets, advancing, approving and cancelling a pipeline, creating, changing and deleting schedules, `POST /registry/sync-workflows|enable|disable`, `POST /packs/{pack}/{template}/run`, resuming, cancelling, expiring and sending control to a run, `POST /runs/{id}/events/ingest`, `POST /approvals/dismiss`, `POST /triggers/alert|pattern|manual` and `POST /triggers/approve/{workflow_id}`. On `POST /runs/{id}/events/ingest` a per-run worker token is not checked against the workspace: the auth guard already limits it to its own run. The middleware still answers first (`404` for a workspace the caller's account does not own), so a caller it lets through is unchanged. The check runs before the request body is validated, so a caller who may not write there gets `403` even for a malformed body (on `POST /start` and the variable writes this was a `422`). With auth off, a workspace that another account owns (one created while auth was on) now refuses these writes and inbox replay with `403`, as `POST /start` already did; workspaces created with auth off belong to the default account and are unchanged. Not covered: account-level routes (`/auth/*`, `/workspaces`), signed webhook receivers, side-effect-free previews, and the pull-lane routes (`/jobs/claim`, `/jobs/{id}/heartbeat`), which act in no workspace; who may claim or heartbeat a job is tracked separately.
- Connection and secret resolution is scoped to the run's account (the owner of the run's workspace). Looking a connection up by name (`resolve_connection`, an operator's `compute_target`, a remote job's compute in the control worker, the per-target concurrency cap, the model licence gate's token check, preflight's connection warnings, the templates contract) finds only rows of that account: a tenant's run finds only its own connections, and the deployment's run (`default`) only the deployment's. `resolve_connection` takes an optional keyword `account_id`; omitted, it is the current run's. An operator's declared secrets for a tenant run come only from that account's connections and reach the operator through `ctx.secrets`; they are no longer written to the process environment, and the deployment's bound SecretStore is not read for a tenant run (`build_scoped_secrets(..., account_id=, values=)`, `declared_secret_values`). Template runs, in-process resumes, pipeline legs (in-process and under the Temporal owner) and remote-job polls run in the workspace their record names; with auth on, a record that names no workspace, or a workspace no store holds, is refused instead of resolving as the deployment, and so is a lookup made with auth on outside any workspace scope (`WorkspaceScopeRequired`); a tenant's flow legs run on targets in its own account. `cairn connect test`, `cairn doctor` and `cairn compute status` look up the deployment's connections. Work an operator starts from inside a run (`ctx.launch`) starts in the run's workspace, and with auth on and no workspace in scope it is refused. With auth on, a pipeline step whose record names no workspace ends failed (verdict `workspace_unresolved`) and fails its pipeline once. ADR-0143 records how declared secrets apply to a tenant run. Single-node and auth-off deployments, where everything belongs to `default`, are unchanged. Behaviour change for tenant runs: a connection name that only the deployment holds no longer resolves, and an operator that reads a credential from `os.environ` receives none; it must read `ctx.secrets`.
- Connection secrets are scoped to the account that owns the connection. A connection of an account other than the deployment's `default` resolves only secret references stored for that account: a bare environment-variable name or `${env:NAME}`, the deployment's own stored secrets, the bound SecretStore and another account's references resolve to nothing, and its OAuth token is read under its own name. New references for an account are namespaced (`mint_ref(..., account_id=...)` gives `cairn://secrets#<account>/<conn>-<KEY>`). `resolve_secret`, `put_secret` and `connection_from_provider` take an optional `account_id`: with one, `put_secret` and `connection_from_provider` refuse a reference from outside the account, and `connection_from_provider` no longer applies the catalog defaults that name server environment variables. Without an account, or with `default`, nothing changes, and references stored before this release keep resolving for the deployment. A tenant connection that holds an older un-namespaced reference resolves it to nothing until its credential is entered again.
- `mcp_server_spec` fails closed. It builds a `stdio` spec only when the caller passes `allow_stdio=True`, and an http/sse `url` must pass the connection probe's address guard (no loopback, link-local, cloud metadata or, unless `CAIRN_PROBE_ALLOW_PRIVATE` is set, private address) unless the caller passes `allow_private_network=True`; otherwise it raises `ValueError`. A caller that serves the deployment's admin passes both to keep today's behaviour. Without `allow_private_network` the spec carries an `httpx_client_factory` (`no_redirect_http_client`) whose client does not follow redirects, so a checked URL cannot redirect the client elsewhere; such a spec holds a callable and is no longer JSON-serialisable. With it the spec is unchanged.
- A knowledge corpus source (`resolve_corpus_source`, `index_workspace_corpus`) is cloned only from a public `https://` git URL by default: the address must pass the connection probe's guard, git is limited to https and does not follow redirects, and `--` ends git's options before the URL. `file://` sources, local paths and ssh or `file:` git remotes need `allow_local=True`, which only a deployment caller should pass; an option-shaped source or a `<transport>::` remote is always refused. Indexing a `file://` source whose path ends in `.git` no longer deletes that directory afterwards. Without `allow_local` the clone also runs without the server's system and global git config (credential helpers, extra headers, URL rewrites), with no credential helper, no askpass and no terminal prompt, in an allowlisted environment (`PATH`, `LANG`/`LC_*`, `TMPDIR`, the proxy variables and the CA-bundle variables) with `HOME` and `XDG_CONFIG_HOME` set to an empty temporary directory. Behaviour change: a tenant clone ignores the deployment's gitconfig, including an `http.proxy` or `http.sslCAInfo` set only there; set `HTTPS_PROXY` / `SSL_CERT_FILE` (or `GIT_SSL_CAINFO`) in the environment instead, which tenant clones still use.
- Breaking default for library callers: `mcp_server_spec`, `resolve_corpus_source` and `index_workspace_corpus` now default to the tenant-safe behaviour above. Code that calls them on the deployment's own behalf and relied on stdio servers, internal MCP URLs or local / ssh corpus sources must now pass `allow_stdio=True`, `allow_private_network=True` or `allow_local=True`.
- Known limits of the address guard used by the connection probe, MCP specs and corpus clones: the host is resolved once, before connecting, so a DNS answer that changes in between (DNS rebinding) is not caught, and a host that does not resolve at check time passes. `CAIRN_PROBE_ALLOW_PRIVATE` lifts the private-address rule for tenant MCP URLs and corpus clones as well as for the probe; loopback, link-local and cloud-metadata addresses stay refused.
- Claiming pull-lane work needs a worker-pool credential or the deployment admin. With auth on, claiming (`POST /jobs/claim`) and heartbeating a job need the deployment's admin (`CAIRN_API_USER`) token or a worker-pool token; a user's token gets `403` whatever their account or role. A per-run worker token still heartbeats its own run's job only. Auth off is unchanged. New: `cairn remote worker-token --name <name> [--days N]` prints a worker-pool token (claims `scope=worker-pool`, `sub=worker-pool:<name>`, default 30 days), signed with the deployment's `CAIRN_JWT_SECRET`, so run it where that secret is set. The auth guard limits a worker-pool token to `POST /jobs/claim` and `POST /jobs/{id}/heartbeat` (`403` elsewhere). Upgrade: a pull worker that ran `cairn worker --pull --token` with a signed-in user's token must switch to a worker-pool token (or the deployment admin's).
- `POST /registry/install` and `POST /registry/uninstall` act on the whole deployment (a pack is process-wide), and with auth on need the deployment's admin (`CAIRN_API_USER`); anyone else, an account owner or admin included, gets `403`. Auth off is unchanged.
- `POST /triggers/approve/{workflow_id}` checks that the saga belongs to the caller's account, not only the workspace the caller acts in. The route asks the action handler for the saga's workspace (`workspace_of(workflow_id)`, sync or async) and answers `404` unless the caller's account owns that workspace. A handler without `workspace_of` cannot say whose a saga is, so with auth on only the deployment's admin (`CAIRN_API_USER`) decides its sagas; everyone else gets `404`. The deployment's admin still decides any saga, and auth off is unchanged. Upgrade: a deployment whose action handler pauses sagas for approval needs a handler that implements `workspace_of` for account members to keep deciding them.
- Knowledge corpora and retrieval are scoped to the workspace. Role composition (`list_roles`, `resolve_role`, and through them ambient knowledge and `compose_knowledge`) lists the installed packs' corpora plus the current workspace's own corpora. `list_roles` takes an optional keyword `workspace` (default: the current workspace), and `workspace_corpus_targets_sync()` without an argument reads the current workspace's corpora instead of every workspace's. `index_workspace_corpus` indexes a corpus into its own workspace's collection whichever context calls it, and a corpus target's `collection` names that collection. A workspace whose id is not a lowercase slug (`[a-z0-9]` runs joined by single dashes) now gets the vector-collection prefix `ws__<hash>__`, so no two workspaces share a prefix; the `default` workspace and slug ids keep their collection names, so existing collections need no migration. Upgrade: a workspace with a non-slug id indexes its corpora again (its episodic memory starts empty under the new name; the old tables are left in place, not deleted). A workspace corpus indexed from outside its workspace before this release (for example from the CLI) should be indexed again so it lands in its workspace; the earlier index is not removed from the `default` workspace's collection of that name automatically.
- The process-wide RAG vector store and the episodic-memory store are used one collection operation at a time. A store keeps the collection it acts on as instance state, so each store call (a search, an upsert batch, a delete, a source check or listing) now selects its collection and runs while holding that store's lock (`cairn.services.rag.stores.on_collection`, `StoreLock`). Only the store call holds it: parsing, embedding, catalog writes and answer synthesis run outside, and an index run takes it one document's store call at a time. Waiters are served in arrival order; a caller that waits longer than 30 seconds gets `VectorStoreBusy` ("knowledge store busy, try again"). A caller with no running asyncio task gets `RuntimeError`. Each store creates (or checks) a collection once per process, not on every call. The `rag/search` and `memory/search` operators keep one store per collection and are unchanged.
- New workspace ids are at most 40 characters (`MAX_WORKSPACE_ID_LEN`). `POST /workspaces` and an account's first workspace cut a longer slug (an explicit `id` included) to 40 characters, and the `-2`, `-3` dedupe stays within them. A workspace's collection names begin with its id, and Postgres keeps only the first 63 bytes of a name: with the cap the workspace part always fits. An existing slug id longer than 40 characters now gets the `ws__<hash>__` collection prefix, so a workspace with such an id indexes its corpora again (its episodic memory starts empty under the new name; old tables are left in place). Existing ids are not renamed. A knowledge corpus name is at most 48 characters (`MAX_CORPUS_NAME_LEN`): every corpus store's `add` raises `ValueError` for a longer one, and `corpus_name_problem(name)` lets a caller check first.
- In the `default` workspace, `workspace_collection` raises `ValueError` for a name that starts with `ws_`, the prefix every other workspace's collections carry; the `default` workspace's own names are bare and never start with it.
- pgvector stores a collection whose name is longer than 63 bytes (Postgres keeps only the first 63 bytes of an identifier) in a table named by a readable 40-byte head plus a 16-hex SHA-256 of the whole name (`pg_table_name`), so long corpus names and different embedder fingerprints keep separate tables. Index names stay `<table>_embedding_idx` / `<table>_source_idx` cut to 63 bytes, as Postgres already named them; a table whose name is 62 or 63 bytes long, where those cut names coincide, now gets hashed index names, so both of its indexes are created. Names within 63 bytes are unchanged, and SQLite keeps names whole and is unchanged. Upgrade: a pgvector collection whose name was longer than 63 bytes starts as a new, empty table; the old table is left in place. A git-sourced workspace corpus is embedded again on its next index (each clone is read from a new path). A corpus read from a stable path (a `file://` workspace corpus, a pack corpus, a directory indexed from the CLI) is skipped by the incremental index while its catalog entries say it is indexed, and there is no force-reindex flag: delete its rows from the `rag_catalog` table (`DELETE FROM rag_catalog WHERE corpus = '<key>'`, where `<key>` is `<pack>/<corpus>` for a pack corpus or `ws:<workspace>/<corpus>` for a workspace corpus, preceded by the workspace's collection prefix such as `ws_<workspace>__` outside the `default` workspace), then index it again (`index_corpus` / `index_all` for pack corpora, `index_workspace_corpus` for a workspace corpus).

### Changed
- `cairn run --mock` returns a deterministic response for every LLM call and runs operators that declare `supports_mock` through `.mock()`; it needs no provider key or endpoint. It refuses before any node runs when a reachable operator does not declare mock support, naming those operators. Before, a prompt node's model call was still made (#62, #164).
- The example pack `cairn-pack-hello` is 0.2.1: the `ask-the-docs` pipeline comments and the pack README describe the `--mock` dev loop.

### Fixed
- Nested pipeline wires are validated at plan time. A `$steps.<id>.<field>` inside a `with:` map or list must name a known step that runs earlier, and a nested `$input.<name>` must name a declared input; a bare `<id>.<field>` inside a map or list is refused as ambiguous (write `$steps.<id>.<field>`). Top-level bare wires still work (#158).

## [0.1.4] - 2026-10-21

### Security
- The auth guard decides on the request path the router serves (`scope['path']`), not on `request.url.path`, which is rebuilt from the Host header and cut at a decoded `?` or `#`. A request to a protected route that names a public path that way now answers 401. The base dependencies require `starlette>=1.0.1`, the first release that ignores a malformed Host header when it builds `request.url`.
- A webhook signature header with non-ASCII characters is refused with 401; it answered 500.
- The pull-lane jobs router scopes a token exactly as the auth guard does: a token carrying `scope=run-ingest` is limited to its own run's job whatever its subject, so heartbeating another run's job answers 403 (it was treated as an operator credential there).
- The durable trigger inbox is scoped to the caller's workspace. `GET /triggers/inbox` listed every workspace's queued deliveries, inputs included, to any signed-in user; it now lists only the caller's workspace (a delivery with no workspace belongs to `default`). `POST /triggers/inbox/replay` re-enqueued every workspace's deliveries for any signed-in user; it now needs an owner or admin (`403` otherwise) and replays only the caller's workspace. The deployment's admin (`CAIRN_API_USER`) still replays every workspace's.
- With the durable trigger inbox on (`CAIRN_TRIGGER_DURABLE`), a queued webhook delivery starts through the same launch door as an inline one. The drain compiled and ran the named template in process, with no policy gates, admission, budget reservation or run record, and could not start a declared pipeline at all (`pipeline:` refs failed and were dead-lettered). Queued deliveries now create a pipeline record and a run per leg, reserve budget where the launch door does (template and flow legs), and a policy `deny` or a ref that names no pipeline refuses them.
- With the durable trigger inbox on (`CAIRN_TRIGGER_DURABLE`), a queued webhook delivery keeps the workspace of the receiver that matched it, and its run starts there; it started in the default workspace. A replayed delivery keeps it too. Deliveries queued by an older server still start in the default workspace, and so does a delivery that a consumer on an older version takes from a shared NATS inbox (it ignores the new field).
- A workspace can no longer take another workspace's webhook. Enabling the same pipeline in a second workspace used to replace the first workspace's trigger record and move it, because trigger ids and names are global. Now a declared webhook whose path, id or name another workspace already holds is not armed, and the server logs an error naming the path and both workspaces. The trigger store refuses such a write (`TriggerOwnedByAnotherWorkspace`) from any caller. If records from two workspaces still reach the server at one path, no receiver is mounted there. A workspace's webhook still replaces a pack or overlay receiver at the same path.
- Only the owning account manages a workspace. `DELETE /workspaces/{id}` and `PATCH /workspaces/{id}` archived or restored any workspace for any signed-in user; they now need an owner or admin (`403` otherwise) of the account that owns the workspace, and another account's workspace answers `404`, the same as a missing one. `POST /workspaces` with an id that already exists replaced that workspace and stamped it with the caller's account, `default` included, which handed the caller its runs, variables and starts and locked the owner out; an explicit `id` now answers `404` when another account holds it and `409` when the caller's own account does; a create by name takes the name's first free slug (`ops-2`). The check reads before it writes, so two concurrent creates of the same fresh id can still race (a create-only store write is a follow-up). The deployment's admin (`CAIRN_API_USER`) still archives and restores any workspace; auth off is unchanged for archive and restore.
- With auth on, a workspace id that no workspace store holds is refused with `404`, the same answer as a workspace another account owns. Any signed-in user could name an id nobody had created and read or write records under it (runs, variables, pipeline starts), and whoever later created a workspace with that id inherited them. Create a workspace (`POST /workspaces`, sign-up, or the first OAuth sign-in) before naming it. Auth off is unchanged. With auth on, `CAIRN_WORKSPACE` must name an existing workspace (`default` always exists); a workspace named while auth was off but never created is unreachable until it is created with `POST /workspaces`.
- With auth on, a request that names no workspace (no `/workspaces/<id>/` path, no `X-Cairn-Workspace` header) is held to the workspace it acts in. It acted in the server's default workspace (`CAIRN_WORKSPACE`, else `default`) for every signed-in user, so a member of any account could read that workspace's runs, pipelines and other records. A caller whose account owns that workspace is unchanged; any other caller now acts in their account's oldest active workspace, the one sign-in opens. An account with no active workspace gets `404` on every workspace-scoped route; it can still sign in, list, create and restore its workspaces (`/auth/*`, `/workspaces`, `/workspaces/{id}`) and list operator reports. A `CAIRN_WORKSPACE` with no workspace record is a misconfiguration with auth on (the server logs a warning at startup): it sends every header-less caller to their account's oldest active workspace, which for the default account is normally `default`. A header-less `POST /start` from another account's caller launches in that workspace; it answered `403`. If an authenticated caller's account cannot be resolved, the request answers `503` instead of proceeding, whether or not it names a workspace. Otherwise naming a workspace, auth off, public routes and signed webhooks are unchanged. The deployment's admin (`CAIRN_API_USER`) and per-run worker tokens belong to the default account, so they are unchanged unless `CAIRN_WORKSPACE` names a workspace another account owns or one with no record: then a header-less request from them acts in the default account's oldest active workspace instead, and a worker reporting a run in `CAIRN_WORKSPACE` without a header gets `404`.

### Changed
- The installer (`https://docs.cairndev.sh/install.sh`) installs from PyPI by default; every package is published there from 0.1.3. `CAIRN_RELEASE=<version>` still takes cairn's wheels from that GitHub Release, which is the way to install a version before 0.1.3.
- The CI gate examples (`examples/ci/`) install `cairndev`; they named the bare `cairn` distribution, which on PyPI is an unrelated project.

## [0.1.3]

### Security
- The server's access log no longer records a bearer token sent in the query string: on the run event stream, which accepts `?access_token=`, the value is logged as `***`.
- Webhook receivers live under `/triggers/`. A receiver whose path collides with an app route is refused, a receiver is public only for its own method and only with a non-empty signing secret, and its runs land in the workspace that declared it (#141).

## [0.1.2]

### Security
- A bearer token in the URL (`?access_token=`) is accepted only on the run event stream; anywhere else it is refused (401).
- A per-run worker token reaches only its own run's reporting routes (events, control, heartbeat); anything else answers 403.
- A webhook receiver answers without a cairn token only when its signature is required; an optional-signature receiver stays behind sign-in.
- The OAuth callback is reachable without a token (the provider's redirect carries none) and escapes everything it shows; the saga approval decides on `POST /triggers/approve/{id}` only.
- The workspace check covers the credential the auth guard accepted, so a token for one workspace cannot read another workspace's run stream.

### Fixed
- The quickstart's `cairn remote login` failed on a plain install with "password hashing needs the 'auth' extra": `cairn dev` turns on password sign-in, so `pwdlib[argon2]` is now a base dependency (the `auth` extra still works and installs nothing more).
- `cairn dev` and `cairn remote` start the engine with `python -P`, so a `cairn/` folder in the working directory (a checkout) is never imported in place of the installed engine.
